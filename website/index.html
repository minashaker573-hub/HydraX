The field problem

Most irrigation systems know when to run.
They don't know why.

A timer cannot see rainfall, a heatwave, a blocked line or a probe that has failed. And on most farms, the four things that would explain what is actually happening never end up in the same place.

01

Soil

Moisture changes zone by zone, hour by hour. Rarely measured, almost never logged.

02

Pump

Runs on a schedule or a switch someone flips, with no view of what the soil needed.

03

Water

Flows or doesn't, but a stuck valve or a burst line often goes unnoticed for hours.

04

People

Find out last — usually by seeing the result in the field, not the cause behind it.

HYDRAX exists to close that loop on the controller itself — soil reading in, irrigation decision out, on the same device, without waiting on a network round trip to a backend that might not even be reachable.

How HYDRAX thinks

One control loop, running entirely on the controller.

Every stage below executes on the ESP32, once a second. The backend and dashboard observe this loop; they are never a step inside it.

01

Sense

Two capacitive probes per zone, median-filtered against spikes and checked against a plausible electrical range before anything trusts the number.

02

Understand

A zone's moisture is the mean of the probes that are actually working. A failed probe is excluded, never averaged in as zero.

03

Decide

Starts below a start threshold, stops at a higher stop threshold. The gap between them is deliberate — a single setpoint would chatter the pump.

04

Act

The zone valve opens first, the pump follows — never the reverse. One zone at a time. A maximum runtime bounds the worst case.

05

Monitor

Readings and events publish to the dashboard. Offline, they buffer on the device and flush on reconnect — irrigation does not wait for either.

The system

Four links, in one direction.

Zone count, pins and thresholds are configuration, not code — the current build covers two zones, and the architecture is not limited to that number.

  1. Soil sensors

    Four capacitive probes, two per zone, sampled and filtered on the device.

  2. ESP32 controller

    Runs the irrigation state machine and holds every safety interlock.

  3. Zone valves

    One open at a time, driven through a relay stage the controller never bypasses.

  4. Irrigation

    Water reaches exactly the zone the controller opened a valve for — nowhere else.

Hysteresis, not a setpoint

Irrigation starts below a start threshold and stops at a higher stop threshold. A single setpoint would switch the pump on and off repeatedly at the boundary.

Runtime protection

A maximum runtime cuts the pump if a run goes long, and locks the zone out until it has been reviewed — bounding the worst case rather than trusting the happy path.

Cooldown

A minimum time between runs on the same zone is enforced independently of the threshold band, so a noisy reading cannot restart a zone immediately.

Built for the field

What the system actually does today.

Every line below is implemented and covered by the automated firmware test suite — see Engineering status for the count.

01

Local-first

The irrigation controller holds no reference to Wi-Fi or HTTP. A host test runs a complete irrigation cycle with no network object present at all, at any point in the process.

02

Zone-based

Each irrigation zone has its own thresholds and its own state, monitored and served independently.

03

Hysteresis

A start/stop band, not a single setpoint, reduces unnecessary switching right at the threshold.

04

Runtime protection

The controller limits how long a zone can run continuously, per the implemented safety logic.

05

Offline operation

Critical irrigation logic does not depend on internet availability — the controller decides alone.

Engineering status

Where the project actually stands.

Stated plainly, split the way it should be judged — because a reviewer can check every line of it against the repository.

Verified in software

Control firmware

Sensing, calibration, filtering, fault handling, zone logic, the irrigation state machine and every safety interlock — 50 host tests, 1,082 assertions.

Backend and dashboard

Telemetry ingestion with strict validation, history, events, alerts, and the seven-section monitoring interface — 129 backend tests.

Cross-compiled for the target

The firmware builds clean for the ESP32 across four configurations: device, simulation, bench-timing and commissioning.

Pending hardware validation

On-target execution

The firmware compiles for the ESP32; it has not yet run on one. A written commissioning and fault-injection procedure exists and is ready for it.

Per-probe calibration

Each capacitive probe needs a dry/wet reference taken from the real unit before its reading means anything — that requires the physical probe in hand.

Flow measurement and pump condition

No flow meter, current sensor or vibration sensor exists in the current bill of materials — the prerequisite for either water accounting or condition monitoring.

A design decision worth stating

We have not published a water-saving figure, and will not until we have measured one. Doing that credibly needs a flow meter, a control plot on the existing schedule, and a full season of data — none of which exist yet. Predictive maintenance and leak localization are architected for, not implemented, and neither is claimed here.

The same rule governs every reading with no sensor behind it: it displays NOT AVAILABLE, not a zero and not an estimate. That is the actual interface — see the capture above.
